Ticket: #92

## Why

訂單狀態只有四種值，但後台訂單列表的訂單狀態篩選仍以任意字串傳遞，同一組篩選的訂單來源已是有限值型別。寫錯的值不會被擋下：系統回 200 與空列表，看起來像「沒有訂單」，型別檢查與 OpenAPI 文件也都看不出有效值。

## What Changes

- 訂單狀態以單一有限值型別表達，後台列表篩選的 API、service、repository 與變更訂單狀態的請求都使用它，與訂單來源相同。
- **BREAKING** 訂單狀態篩選值不是四種訂單狀態之一時，由回 200 與空列表改為回 422，與訂單來源及變更訂單狀態的行為一致。
- OpenAPI 文件把訂單狀態篩選參數宣告為 enum。
- 後台介面不變：它只送四種訂單狀態，選「全部」時不帶參數。

## User Stories

1. 身為開發者，我想要訂單狀態篩選與訂單來源使用同樣的有限值型別，以便型別檢查能擋下寫錯的值。
2. 身為管理員，我想要帶錯的訂單狀態篩選值時得到錯誤，以便不會把「值寫錯」誤認成「沒有訂單」。
3. 身為 API 使用者，我想要在 OpenAPI 文件看到訂單狀態篩選的有效值，以便不用翻程式碼。

## Capabilities

### New Capabilities

無。

### Modified Capabilities

- `admin-orders`: 移除「訂單狀態篩選值不驗證」，改為無效的訂單狀態篩選值回傳 422。

## Impact

- 後台訂單列表 API：無效的訂單狀態篩選值改回 422，空字串同樣視為無效；OpenAPI 參數改為 enum。
- 後端型別：新增訂單狀態型別，route、service、repository 與變更訂單狀態的 schema 改用。
- 無 migration、無前端變更、無新相依。
