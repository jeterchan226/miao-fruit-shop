# 後端一律以 UTC 時點存取與比對，時區換算由前端負責

後端只處理 timezone-aware 的時點：資料庫存 `timestamptz`，API 收送的時間一律帶時區（ISO 8601，`Z` 或 `+08:00`），不帶時區的 datetime 或純日期回 422。「某一天」這種依地點而異的概念不進後端；前端依使用者瀏覽器當前時區，把選到的日期換算成 UTC 時間範圍（當日 00:00 含、隔天 00:00 不含）再送出。後台訂單篩選因此以 `created_from` / `created_before` 取代原本的 `date_from` / `date_to`。

起因是原本後端拿 `date` 跟 `timestamptz` 比，等於用 UTC 午夜切日，台北凌晨 00:00–08:00 的訂單被歸到前一天；本機測試也因依賴 `date.today()` 而在台北凌晨失敗。

## Considered Options

- 後端寫死 `Asia/Taipei` 切日：目前使用者都在台灣，但把時區藏進後端，測試與日後跨時區使用都會再踩同一個坑，否決。
- API 收日期加時區名稱參數（如 `tz=Asia/Taipei`）由後端換算：多一套時區資料與驗證在後端，且前端本來就知道使用者時區，否決。
